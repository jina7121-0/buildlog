# BuildLog MVP 개발 계획

## 1. 계획의 목적

이 문서는 `spec.md`에 정한 BuildLog 기능을 FastAPI, React, Supabase, SQLite3로 어떤 순서에 따라 개발할지 설명합니다.

한 번에 Phase 하나만 진행하고, 해당 Phase의 확인 기준을 모두 통과한 뒤 다음 Phase로 넘어갑니다. `spec.md`에 없는 기능은 추가하지 않습니다.

## 2. 확정된 기술과 환경

| 구분 | 사용할 기술 |
| --- | --- |
| 백엔드 | Python, FastAPI |
| 프론트엔드 | React |
| 운영 데이터베이스 | Supabase |
| 개발·자동 테스트 데이터베이스 | SQLite3 |
| 날짜와 시간 | 한국 표준시(`Asia/Seoul`) |

- React 화면은 FastAPI API를 통해 데이터를 읽고 저장합니다.
- Supabase는 운영 데이터베이스로 사용합니다.
- 회원가입, 로그인, 기록 권한과 입력 검사는 FastAPI 백엔드에서 처리합니다.
- SQLite3와 Supabase에서 같은 기능이 동작하도록 공통 데이터 접근 구조를 사용합니다.
- 실제 비밀값은 `.env`에 두고 `.env.example`에는 항목 이름과 비밀값이 아닌 예시만 기록합니다.
- 실제 SQLite3 데이터 파일, `.env`, `.venv`, `node_modules`, `dist`, 캐시와 로그는 Git 기록 대상에서 제외합니다.
- Git 초기화와 커밋은 별도 요청이 있기 전까지 수행하지 않습니다.

## 3. 예정된 프로젝트 구조

정확한 파일 이름은 Phase 0에서 선택한 안정 버전과 도구에 맞춰 확정합니다. 폴더의 역할은 다음과 같습니다.

```text
buildlog/
├─ backend/
│  ├─ app/
│  │  ├─ main.*          # FastAPI 시작점
│  │  ├─ api/            # 회원, 기록, 공개, 댓글, 좋아요, 신고 API
│  │  ├─ models/         # 데이터 구조
│  │  ├─ schemas/        # 요청과 응답 데이터 조건
│  │  ├─ services/       # 기능별 처리 규칙
│  │  ├─ db/             # Supabase·SQLite3 연결
│  │  └─ core/           # 환경 설정, 인증, 시간대, 공통 기능
│  ├─ migrations/        # 데이터 구조 변경 기록
│  └─ tests/             # 백엔드 자동 테스트
├─ frontend/
│  ├─ src/
│  │  ├─ pages/          # 화면
│  │  ├─ components/     # 공통 UI
│  │  ├─ api/            # FastAPI 호출
│  │  └─ styles/         # 공통 디자인
│  ├─ public/
│  └─ package.json
├─ database/
│  └─ buildlog.sqlite3   # 개발용 파일, Git 제외
└─ docs/                 # 요구사항, 동작 설명서, 개발 문서
```

## 4. 개발 원칙

- 각 Phase에서 정상 동작, 잘못된 입력, 실패 처리, 권한을 함께 구현합니다.
- 버튼을 숨기는 것만으로 권한을 처리하지 않고 FastAPI에서도 반드시 확인합니다.
- 프론트엔드는 사용자가 이용할 수 없는 기능을 보여주지 않으며, 백엔드는 잘못된 직접 요청도 거부합니다.
- 비밀번호 원문과 데이터베이스 비밀값을 코드, 문서, 화면, 로그에 남기지 않습니다.
- 자동 테스트는 SQLite3로 빠르게 실행합니다.
- 운영 전에는 같은 데이터 구조를 Supabase에 적용하고 핵심 흐름을 다시 확인합니다.
- 날짜와 시간은 한국 표준시를 기준으로 사용자에게 보여줍니다.
- 각 Phase가 끝날 때 백엔드 자동 테스트와 실제 브라우저 확인을 함께 수행합니다.
- 확인에 실패하면 다음 Phase로 넘어가지 않습니다.

## 6. Phase별 상세 계획

### Phase 0. 개발 시작 전 기준 확정

**상태: 완료 — 2026-10-26**

#### 목표

코드나 패키지를 변경하기 전에 현재 환경을 읽기 전용으로 확인하고, FastAPI와 React 프로젝트를 만들 때 필요한 기술 선택과 설정 이름을 확정합니다.

#### 작업

1. `MVP.md`, `PRD.md`, `spec.md`, `plan.md`의 기능과 기술 구성이 서로 맞는지 확인합니다.
2. 첫 버전에서 만들지 않는 기능을 다시 확인합니다.
   - 이메일 확인
   - 비밀번호 찾기
   - 할 일 마감일과 중요도
   - 내 할 일 검색
   - 댓글 답글
3. 현재 설치된 Python, Node.js, npm 실행 여부와 버전을 읽기 전용으로 확인합니다.
4. 서로 호환되는 안정 버전의 FastAPI와 React 도구를 선택합니다.
5. React는 TypeScript로 작성합니다.
6. SQLite3와 Supabase를 모두 지원할 데이터 연결 및 변경 관리 도구를 확정합니다.
7. 프론트엔드와 백엔드의 로컬 개발 서버 주소를 정합니다.
8. React가 FastAPI를 호출할 수 있도록 허용할 로컬 주소를 정합니다.
9. 인증 정보를 안전하게 전달하고 유지할 방식을 확정합니다.
10. 다음 환경 변수의 이름과 용도를 정리합니다.
    - 실행 환경 구분
    - 비밀키
    - 데이터베이스 연결 주소
    - 프론트엔드 허용 주소
    - 시간대
11. 개발·테스트용 SQLite3 파일 위치를 `database/buildlog.sqlite3`로 확정합니다.
12. 시간대를 `Asia/Seoul`로 확정합니다.
13. 테스트 명령, 백엔드 실행 명령, 프론트엔드 실행 명령을 기록할 문서 위치를 정합니다.

#### 사용자에게 필요한 내용

- React는 사용자 선택에 따라 TypeScript로 확정했습니다.
- Supabase 프로젝트 주소와 데이터베이스 비밀번호는 Phase 13의 운영 연결 전까지 필요하지 않습니다.
- Supabase 비밀값은 채팅이나 문서에 보내지 않고, 나중에 사용자가 로컬 `.env`에 직접 입력합니다.

#### 예상 변경 파일

- `docs/plan.md`
- 필요 시 `docs/setup.md`
- 이 Phase에서는 코드, 패키지, 데이터베이스를 변경하지 않습니다.

#### 확인 방법

- 네 문서에서 이전 기술 구성을 전제로 한 설명이 남아 있지 않은지 확인합니다.
- Python, Node.js, npm의 현재 상태를 확인합니다.
- 운영 DB와 테스트 DB의 역할이 섞이지 않았는지 확인합니다.
- 모든 필요한 환경 변수에 비밀값이 아닌 이름과 설명만 준비되었는지 확인합니다.

#### 완료 조건

- [x] 기능 범위와 기술 구성에 충돌이 없습니다.
- [x] React 언어와 개발 도구가 TypeScript와 Vite로 확정되었습니다.
- [x] FastAPI와 React의 안정 버전 기준이 정해졌습니다.
- [x] Supabase와 SQLite3의 공통 데이터 접근 방법이 SQLAlchemy와 Alembic으로 정해졌습니다.
- [x] 로컬 서버 주소, 인증 방식, 환경 변수 이름이 정해졌습니다.
- [x] 코드나 패키지는 변경하지 않았습니다.

### Phase 1. FastAPI·React 프로젝트 뼈대 만들기

**상태: 완료 — 2026-10-26**

#### 목표

기능이 없는 상태에서 FastAPI 백엔드와 React 프론트엔드를 각각 실행하고, React가 FastAPI의 상태 확인 API를 호출할 수 있게 합니다.

#### 작업

1. `backend/.venv`에 Python 가상환경을 준비합니다.
2. FastAPI 실행에 필요한 최소 패키지만 설치하고 버전을 기록합니다.
3. `backend/app`에 FastAPI 시작점과 기본 설정 구조를 만듭니다.
4. 백엔드 상태 확인 API 하나를 만듭니다.
5. `frontend`에 React 프로젝트를 준비합니다.
6. React 기본 화면에서 백엔드 상태 확인 API를 호출합니다.
7. 로컬 개발 주소 사이의 요청을 허용하도록 백엔드를 설정합니다.
8. 시간대 기본값을 `Asia/Seoul`로 설정합니다.
9. `.env.example`에 비밀값 없이 필요한 항목 이름을 기록합니다.
10. 생성 파일과 SQLite3 실제 파일을 `.gitignore`에 보완합니다.

#### 확인 방법

- FastAPI 개발 서버가 오류 없이 실행되는지 확인합니다.
- React 개발 서버가 오류 없이 실행되는지 확인합니다.
- React 화면에 백엔드 상태 확인 결과가 보이는지 확인합니다.
- 허용하지 않은 주소에서 오는 요청은 받아들이지 않는지 확인합니다.
- `.env.example`에 실제 비밀값이 없는지 확인합니다.

#### 완료 조건

- [x] FastAPI와 React 개발 서버가 각각 실행됩니다.
- [x] React가 FastAPI API를 호출할 수 있습니다.
- [x] 공통 설정과 시간대 설정을 읽을 수 있습니다.
- [x] 아직 회원이나 기록 기능은 만들지 않았습니다.

### Phase 2. 공통 데이터 연결과 사용자 구조

#### 목표

같은 데이터 구조를 개발·테스트에서는 SQLite3, 운영에서는 Supabase에 사용할 수 있게 만들고 사용자 저장 구조를 가장 먼저 확정합니다.

#### 작업

1. 공통 데이터 연결 계층을 만듭니다.
2. 실행 환경에 따라 SQLite3 또는 Supabase 연결 주소를 선택하게 합니다.
3. 데이터 구조 변경 이력을 관리하는 방법을 설정합니다.
4. 이메일, 안전하게 처리된 비밀번호, 닉네임, 운영자 여부를 저장할 사용자 구조를 만듭니다.
5. 이메일과 닉네임은 각각 중복되지 않게 합니다.
6. 닉네임 2~20자와 허용 문자 규칙을 적용합니다.
7. SQLite3에 첫 데이터 구조를 적용합니다.
8. 테스트가 끝날 때마다 독립된 SQLite3 상태에서 다시 실행할 수 있게 합니다.
9. Supabase 연결 값이 없어도 로컬 개발과 자동 테스트가 가능하게 합니다.

#### 확인 방법

- SQLite3에서 사용자를 저장하고 다시 읽을 수 있는지 확인합니다.
- 같은 이메일이나 닉네임을 중복 저장할 수 없는지 확인합니다.
- 비밀번호 원문이 저장되지 않는지 확인합니다.
- 테스트끼리 데이터가 섞이지 않는지 확인합니다.
- 운영 연결 주소가 없는 상태에서도 테스트가 통과하는지 확인합니다.

#### 완료 조건

- [ ] SQLite3 연결과 데이터 구조 변경이 정상 동작합니다.
- [ ] Supabase 연결을 나중에 추가할 환경 설정이 준비되었습니다.
- [ ] 사용자 저장 규칙 테스트가 통과합니다.

### Phase 3. 회원가입·로그인·닉네임 변경

#### 목표

FastAPI 인증 API와 React 화면을 연결해 사용자가 가입하고 로그인한 뒤 자신의 닉네임을 바꿀 수 있게 합니다.

#### 작업

1. 회원가입 API와 React 회원가입 화면을 만듭니다.
2. 이메일 형식과 중복, 비밀번호 8자 이상, 닉네임 조건을 검사합니다.
3. 가입 성공 시 자동 로그인하고 내 기록 홈으로 이동합니다.
4. 가입 실패 시 이메일과 닉네임은 유지하고 비밀번호는 화면에서 지웁니다.
5. 로그인 API와 React 로그인 화면을 만듭니다.
6. 로그인 성공 시 내 기록 홈으로 이동합니다.
7. 인증 정보가 브라우저에서 안전하게 유지되도록 합니다.
8. 인증이 필요한 API를 로그인하지 않은 사용자가 호출하지 못하게 합니다.
9. 계정 설정 API와 React 화면에서 닉네임을 변경하게 합니다.
10. 사용자 응답에는 이메일이 필요할 때만 포함되게 하고, 다른 사용자에게는 닉네임만 보여줍니다.

#### 확인 방법

- 정상·중복·잘못된 입력의 회원가입을 확인합니다.
- 가입 후 자동 로그인과 홈 이동을 확인합니다.
- 정상 로그인, 잘못된 로그인, 로그인하지 않은 API 요청을 확인합니다.
- 다른 사용자의 닉네임을 바꿀 수 없는지 확인합니다.
- 비밀번호나 인증 비밀값이 화면과 로그에 노출되지 않는지 확인합니다.

#### 완료 조건

- [ ] 회원가입, 자동 로그인, 로그인, 닉네임 변경이 동작합니다.
- [ ] 보호된 API는 로그인한 사용자만 사용할 수 있습니다.
- [ ] React 화면과 FastAPI의 실패 결과가 일치합니다.

### Phase 4. 공부 기록·할 일·오류 기록 데이터 구조

#### 목표

세 종류의 기록과 상태·시간 규칙을 먼저 데이터와 백엔드 수준에서 완성합니다.

#### 작업

1. 공부 기록 구조를 만듭니다.

#### 사용자에게 필요한 내용

- Supabase 프로젝트 생성
- 프로젝트의 데이터베이스 연결 정보 확인
- 비밀값을 로컬 `.env`에 직접 입력
- 비밀값은 채팅, 문서, 커밋에 포함하지 않음

## 7. 실제 진행 방법

1. 첫 작업은 Phase 0만 진행합니다.
2. Phase 0에서는 읽기 전용 환경 확인과 기술 기준 확정만 합니다.
3. Phase 0의 결과를 공유한 뒤 Phase 1부터 실제 코드와 패키지를 변경합니다.
4. 이후에도 한 번에 Phase 하나만 진행하고 완료 결과를 공유합니다.
5. 여러 Phase를 한꺼번에 구현하지 않습니다.
